An `incident` is a deduped group of alerts from your observability stack — Datadog, Grafana, GCP, SigNoz, Better Stack, or a Slack/Discord `@Sonarly` mention. Unlike a bug (a recurring error pattern), an incident represents an alert that fired and is being actively investigated.

## Endpoints

| Method | Path | Returns |
|---|---|---|
| `GET` | `/v1/public/incidents` | List of incident groups, newest first. |
| `GET` | `/v1/public/incidents/{id}` | A single incident. |
| `GET` | `/v1/public/incidents/{id}/runs` | Claude Code investigation runs for an incident. |

`{id}` accepts both `inc_42` and bare `42`.

## List incidents

```bash
GET /v1/public/incidents
```

### Query parameters

| Name | Type | Default | Notes |
|---|---|---|---|
| `limit` | int (1–100) | `20` | Page size. |
| `starting_after` | cursor | — | An `inc_<id>` from a previous page. |
| `severity` | csv | — | `critical,high,medium,low`. |
| `status` | string | — | `active`, `resolved`, or `muted`. |
| `created[gte]` | unix s | — | Only incidents created at/after this time. |
| `created[lte]` | unix s | — | Only incidents created at/before this time. |

### Example

<CodeGroup>
```bash curl
curl -H "Authorization: Bearer $SONARLY_KEY" \
  "https://sonarly.com/api/v1/public/incidents?status=active&limit=20"
```

```typescript Node.js

  "https://sonarly.com/api/v1/public/incidents?status=active&limit=20",
```

## Get an incident

```bash
GET /v1/public/incidents/{id}
```

Returns the full incident object — same shape as items in the list response. Returns `404` if the incident doesn't exist or belongs to a different tenant.

## List runs for an incident

```bash
GET /v1/public/incidents/{id}/runs
```

Every Claude Code investigation tied to this incident group. Each run carries the analysis (title, severity, root cause, fix), repository / branch / PR if applicable, and run lifecycle timestamps.

The `mode` field is `incident` for these runs (vs `bug_fix` for bug runs).

## Bug vs Incident — when to use which

Both resources expose Sonarly analyses, but they model different signals:

| | `bug` | `incident` |
|---|---|---|
| Origin | Recurring error pattern | One-off alert that fired |
| Sources | Sentry, GitHub Issues, Bugsnag, session replay | Datadog, Grafana, GCP, SigNoz, Better Stack, Slack/Discord mentions |
| Lifecycle | `open` → `resolved` → can `reappear` | `active` → `resolved` / `muted` |
| Has occurrence count | Yes (`occurrence_count`) | Yes, but each alert is grouped |
| Identity | `sentry_issue_id` etc. | Group of correlated alerts |
| Webhook events | `bug.*` family | `incident.*` family |

For a unified "all signals" view, query both endpoints and concatenate the results — they share the same envelope and pagination shape.
